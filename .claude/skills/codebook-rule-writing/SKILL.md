# Codebook rule writing

Coders read a rule while looking at a transcript. They arrive with one question: "I have *this* situation — what do I do?" Write every rule so that the coder can find their situation, read one short instruction, and check it against an example.

## The template

Use this shape for any rule that has more than one case:

```
**<Rule name>.** <One sentence that names the job of the rule.>
- **<Case 1, named by the coder's situation>.** <What to do.> <One more point, if needed.>
- **<Case 2>.** <What to do.> <One more point, if needed.>
  <Example, in the codebook's exact output format.>
```

Model (the agreed wording for the order of the label tests in L1.1.3):

> **Applying the labels.** The tests run from the most specific label to the most general.
> - **One span.** The order is a tie-breaker. If the words of one span pass two tests, give the label that comes first in the test order.
> - **Several spans.** Different spans never compete; each gets its own label. Words of different kinds (owning, requesting, disclosing) are always different spans. The order only sets how the labels are listed in Act Type, for example Owning-up: Gap; Seeking: Help.

The earlier draft that this replaced said the same thing in one paragraph and was much harder to read:

> The order decides only when one span passes two tests; it then takes the earlier one. Spans of different kinds (owning, requesting, disclosing) never compete, so the order only sets how their labels are listed in Act Type.

## Rules

1. **Sort by the coder's situation.** Give each case its own bulleted line with a bold lead-in that names the situation ("One span.", "Several spans.", "Teammate asked a question.", "Teammate gave the right version."). Do not mix cases in one paragraph.
2. **One point per sentence.** Split any sentence that joins two claims with "so", "and then", "which means" or a semicolon. The reader should never hold one claim while parsing a second.
3. **Say what to do.** State the action first ("give the label that…", "code Level 1"). Keep "only", "never", "unless" and "not" for limits that matter, and do not stack them in one sentence.
4. **Name the job before the detail.** Open with what the rule is for ("The order is a tie-breaker.") before the condition that triggers it.
5. **End with an example.** Use the codebook's exact output format, with full labels (family and sub-value, for example Owning-up: Gap, never Gap alone), so a coder can copy it.

## Checks before handing over wording

- **No ambiguous pointers.** Write "comes first in the test order", not "appears first" (first in the list, or first in the turn?). Name the section or rule a cross-reference points to, and confirm that it exists.
- **Lead-in matches content.** The sentences under a bold lead-in must cover every situation that the lead-in names, and no other.
- **Codebook vocabulary.** Use the codebook's plain verbs and terms: give, code, list, quote, span, turn, act, label, for example. Avoid "simply", "dictates", "e.g.", "i.e.", "output" (say the field name, such as Act Type), and synonyms for defined terms.
- **Defined terms stay fixed.** Use utterance, turn, vulnerability act, span and label exactly as the Unit of coding defines them. Do not switch between, for example, "span" and "segment".

## Explaining rules in chat

Use the same shape when explaining a rule or a proposed change to the user:
- Give the answer in the first line.
- Put each case on its own labeled line.
- End with an example or a short table that shows the rule applied.
